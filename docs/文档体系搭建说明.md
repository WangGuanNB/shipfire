# 文档体系搭建说明（可复用到其他项目）

> **用途**：本文档描述 ShipFire 项目采用的产品文档结构及维护逻辑。  
> 其他 AI 或维护者可将**同一套规则**迁移到任意业务项目（如 destiny-matrix、astrocartography 等），只需替换产品事实，不必改结构。

---

## 一、设计目标

| 目标 | 说明 |
|------|------|
| **简单** | `docs/` 只有一层，不建子文件夹（除可选的空目录都不需要） |
| **全中文文件名** | 如 `产品说明.md`、`版本0-早期访问.md` |
| **工具无关** | 不绑定 Cursor；任何 AI 读同一套入口即可 |
| **版本驱动** | 用「版本 + 阶段」表达产品升级，而不是散落的多个说明文件 |
| **职责分离** | 产品路线图 ≠ 落地页 SEO ≠ 支付技术 ≠ 站点 YAML 配置 |

---

## 二、目录结构（标准模板）

```text
{项目根}/
├── README.md                    ← 根入口：指向 docs/（保留项目 README 其他内容亦可）
├── my-page-build-factory.yaml   ← 站点事实配置（可选，非 MD）
├── launch.yaml                  ← 落地页 launch 配置（可选，非 MD）
│
└── docs/                        ← 所有 .md 文档统一放这里（一层）
    ├── 产品说明.md              ← 【总纲】产品是什么 + 版本一览表
    ├── 文档维护说明.md          ← 【AI 必读】怎么读、怎么改、怎么维护
    ├── 文档体系搭建说明.md      ← 【可选】本文档，跨项目复用规则
    ├── 版本0-xxx.md             ← 每个大版本一份详情
    ├── 版本1-xxx.md
    ├── 落地页说明.md            ← 专项：落地页模块 / SEO（若有）
    └── 支付集成指南.md          ← 专项：支付等技术（若有）
```

**硬性规则：**

1. 根目录**只保留一个** `README.md`（作为入口），其余 `.md` 一律进 `docs/`。
2. `docs/` **不再分子目录**（不要用 `docs/产品/`、`docs/提案/` 等，保持扁平）。
3. 版本文档命名：`版本{数字}-{简短中文主题}.md`，例如 `版本0-早期访问.md`。

---

## 三、各文件写什么

### 1. `README.md`（根目录）

**职责**：指路牌，不写长篇产品规划。

**必须包含**（约 15～25 行即可）：

- 指向 `docs/` 的说明
- 表格列出：`产品说明.md`、`文档维护说明.md`、当前执行中版本 MD、其他专项 MD
- **AI 阅读顺序**一行话

**示例片段：**

```markdown
## 产品文档

产品与升级规划均在 [docs/](./docs/) 目录。

| 文档 | 说明 |
|------|------|
| [docs/产品说明.md](./docs/产品说明.md) | 产品总览、版本一览 |
| [docs/文档维护说明.md](./docs/文档维护说明.md) | AI / 人类如何维护文档 |
| [docs/版本0-早期访问.md](./docs/版本0-早期访问.md) | 当前执行中版本 |

**AI 建议阅读顺序：** README.md → docs/产品说明.md → 执行中版本 MD → docs/文档维护说明.md
```

---

### 2. `docs/产品说明.md`（总纲）

**职责**：产品「一张表」—— 是谁、做什么、现在哪个版本、有哪些版本。

**固定结构：**

```markdown
# {品牌名} 产品说明

> 最后更新：YYYY-MM-DD
> 线上域名：https://...
> 主关键词：...

## 产品是什么
（一句话定位、目标用户、核心价值、当前形态）

## 当前版本
- **版本**：版本N · {名称}
- **状态**：执行中
- **详情文档**：版本N-xxx.md

## 版本一览

| 版本 | 名称 | 状态 | 说明文档 |
|------|------|------|----------|
| 版本0 | ... | 执行中 | 版本0-xxx.md |
| 版本1 | ... | 未开始 | 版本1-xxx.md |

## 设计原则（可选，简短 3～5 条）

## 相关文档（链接到 docs/ 内其他 MD 和根目录 yaml）
```

**版本状态只允许三个词：**

| 状态 | 含义 |
|------|------|
| 未开始 | 已规划，还没动手 |
| 执行中 | 当前正在做的版本（**同时最好只有 1 个**） |
| 已完成 | 验收通过，不再大改 |

---

### 3. `docs/版本X-{主题}.md`（版本详情）

**职责**：某一个**大版本**的目标、边界、阶段划分、阶段详情。

**固定结构：**

```markdown
# 版本N · {名称}

> **状态**：执行中 | 未开始 | 已完成
> **周期**：YYYY-MM ~ 待定
> **主关键词**：...
> **域名**：...

## 本版本目标
（编号列表，3～5 条）

## 本版本不做
（明确边界，防止 AI 乱加功能）

## 阶段划分

| 阶段 | 内容 | 状态 |
|------|------|------|
| N.1 | ... | 已完成 |
| N.2 | ... | 执行中 |
| N.3 | ... | 未开始 |

## 阶段详情
（每个阶段：目标、验收标准、备注/commit）

## 待评估
（未拍板的想法，checkbox 列表）

## 本版本退出条件
（满足什么后，本版本标「已完成」，下一版本标「执行中」）
```

**阶段状态**同样用：未开始 / 执行中 / 已完成（若阶段很简单，也可只用 未开始 / 已完成）。

---

### 4. `docs/文档维护说明.md`（AI 协作规则）

**职责**：告诉**任何 AI** 如何读、如何改、禁止什么。  
**这是给另一个 AI 调项目时最需要读的文件之一。**

**必须包含的章节：**

1. 文档结构树
2. **AI 阅读顺序**（产品任务 vs 落地页任务 vs 支付任务）
3. **什么时候改哪个文件**（对照表）
4. **禁止事项**
5. **通用开场话术**（复制粘贴即可）
6. 与 `落地页说明.md`、yaml、Skills 的关系

**核心维护规则（务必写进该文件）：**

| 情况 | 做法 |
|------|------|
| 产品定位变了 | 改 `产品说明.md` |
| 当前版本小功能 / 小优化 | 改当前 `版本X-xxx.md`（加阶段或更新状态） |
| 新大版本 | **新建** `版本N-名称.md` + 更新 `产品说明.md` 版本表 |
| 某阶段完工 | 版本 MD 里该阶段 → **已完成** |
| 整个版本验收通过 | 版本 MD + 产品说明版本表 → **已完成**；下一版本 → **执行中** |
| 临时想法、未拍板 | 写在当前版本 MD 末尾 **「待评估」**，**不新建文件** |
| 写落地页 | 读 `落地页说明.md`，不改产品版本文档 |
| 改支付 | 读 `支付集成指南.md` |

**禁止事项（建议原文写入）：**

- 不要改「已完成」版本 MD 的历史内容（除非用户要求勘误）
- 不要在产品说明和版本 MD 里重复大段相同内容
- 不要新建 `docs/` 子目录
- 不要未经用户确认把「待评估」当成已定案
- 不要把产品路线图写进 `落地页说明.md`

**通用 AI 开场话术：**

```text
请先阅读以下文件，再处理我的需求：
1. README.md
2. docs/产品说明.md
3. 产品说明里「执行中」对应的版本 MD
4. docs/文档维护说明.md

我的需求：……
```

（若涉及落地页，追加：`docs/落地页说明.md`）

---

### 5. 专项 MD（按需保留）

| 文件 | 何时需要 |
|------|----------|
| `落地页说明.md` | 项目用 JSON + LandingRenderer 配落地页，且需要 SEO 模块意图 |
| `支付集成指南.md` | 项目有 Stripe/PayPal 等多支付集成 |

专项文档**不放**版本路线图；版本文档里可写「阶段 x.x：改 pricing 文案」并链接到专项 MD。

## 四、与其他资产的分工

```text
docs/产品说明.md + docs/版本X.md     → 产品方向、阶段、升级（总纲）
docs/文档维护说明.md                 → AI 怎么协作
docs/落地页说明.md                   → 页面模块 / SEO 设计（专项）
docs/支付集成指南.md                 → 支付技术（专项）
launch.yaml / my-page-build-factory.yaml → 站点事实（域名、关键词、路由），非 MD
content/docs/*.mdx                   → 【注意】fumadocs 网站 /docs 页面，不是产品总纲
```

**易混淆点：**

- `docs/`（仓库内 MD）= 给人和 AI 读的产品文档  
- `content/docs/`（若存在）= 网站上对外展示的文档页，二者**不要合并**

---

## 五、迁移到新项目的步骤（给 AI 的执行清单）

按顺序执行，**每步完成后更新 `产品说明.md` 的日期**。

### Step 1：摸底

- [ ] 读 `launch.yaml` / `my-page-build-factory.yaml`（若有）获取域名、关键词、定位
- [ ] 读现有根目录 `.md` 文件，列出要迁入 `docs/` 的文件
- [ ] 读 git log 最近 5～10 条，归纳「已经做了什么」→ 填入版本0 已完成阶段
- [ ] 确认是否已有 `content/docs/`（fumadocs），不要与 `docs/` 混淆

### Step 2：创建结构

- [ ] 创建 `docs/` 目录（一层，不建子目录）
- [ ] 创建 `docs/产品说明.md`（填入真实产品事实）
- [ ] 创建 `docs/文档维护说明.md`（可复制本文档第四节规则，改项目名）
- [ ] 创建 `docs/版本0-{当前阶段名}.md`（状态：执行中）
- [ ] 可选：创建 `docs/版本1-{下一里程碑}.md`（状态：未开始，占位）
- [ ] 可选：复制 `docs/文档体系搭建说明.md`（本文档，便于团队统一）

### Step 3：迁移旧 MD

- [ ] 根目录 `落地页说明.md` → `docs/落地页说明.md`（顶部加路径说明）
- [ ] 根目录 `PAYMENT_INTEGRATION_GUIDE.md` → `docs/支付集成指南.md`（或保留英文名，建议中文）
- [ ] 其他产品类 `.md` 内容合并进 `版本X.md` 或 `产品说明.md`，**避免重复文件**
- [ ] 删除根目录已迁移的 `.md`（根目录只留 `README.md`）

### Step 4：更新 README.md

- [ ] 增加「产品文档」小节 + 表格链接
- [ ] 删除指向不存在路径的链接（如已删除的 `.template/`）
- [ ] 更新支付文档等旧路径引用

### Step 5：更新引用

- [ ] 搜索全仓库旧路径（如 `落地页说明.md` 在根目录）并改为 `docs/落地页说明.md`
- [ ] Skills / 工厂调用落地页时，提示显式 `@docs/落地页说明.md`
- [ ] 若有 `my-page-build-factory.yaml`，可加注释指向 `docs/产品说明.md`（可选）

### Step 6：验收

- [ ] 根目录仅 `README.md` 为 MD（其余 MD 均在 `docs/`）
- [ ] `产品说明.md` 有且仅有 1 个「执行中」版本
- [ ] 当前版本 MD 含「本版本目标 / 不做 / 阶段表 / 待评估 / 退出条件」
- [ ] `文档维护说明.md` 含 AI 阅读顺序与禁止事项
- [ ] README 链接均可点击、路径正确

## 六、版本与「突然有个想法」怎么处理

```text
有个新想法
    │
    ├─ 还没想清楚 ──────────→ 先不写，或记在版本 MD「待评估」一行
    │
    ├─ 想清楚了，未拍板 ────→ 写入当前版本 MD「待评估」列表（不新建 MD）
    │
    ├─ 已拍板，小改动 ──────→ 在当前版本 MD 加/改一个阶段
    │
    └─ 已拍板，新大版本 ────→ 新建 版本N-名称.md + 更新 产品说明.md 版本表
```

**不要**为每个小想法单独建 MD 文件；**不要**把未定案内容写进 `产品说明.md` 的「当前版本」当作已在做。

## 八、给「另一个 AI」的简短指令（可直接复制）

```text
请按 ShipFire 的文档体系规则，为【项目名称】搭建/整理 docs/ 文档：

1. 阅读 docs/文档体系搭建说明.md（若在 shipfire 仓库）或按以下结构执行：
   - 根目录 README.md 指向 docs/
   - docs/ 一层目录，全中文文件名
   - 必备：产品说明.md、文档维护说明.md、版本0-xxx.md（执行中）
   - 可选：版本1-xxx.md（未开始）、落地页说明.md、支付集成指南.md

2. 从 launch.yaml / 现有 MD / git log 提取产品事实填入，不要留模板占位符。

3. 根目录除 README.md 外，所有 MD 迁入 docs/，并更新 README 与全仓库引用。

4. 文档维护说明.md 必须包含：AI 阅读顺序、何时改哪个文件、禁止事项、通用开场话术。

5. 完成后输出：新建/迁移文件清单、当前版本阶段表、未解决的待评估项。

不要改业务代码，除非用户明确要求。
```

## 九、维护节奏建议

| 频率 | 做什么 |
|------|--------|
| 每次发版 / 里程碑 | 更新对应阶段状态；必要时改 `产品说明.md` 当前版本 |
| 有新想法 | 先写「待评估」，拍板后再改阶段表 |
| 版本验收完成 | 版本标已完成，下一版本标执行中 |
| 每月可选 | 检查 `产品说明.md` 顶部日期与事实是否仍准确 |
